# calendarBuddy architecture

calendarBuddy is an independent homeBuddy service with a Spring Boot `calendar-api`, a React UI, and its own PostgreSQL database. The [documentation map](README.md) links the service entry points. The root [homeBuddy architecture](../../docs/ARCHITECTURE.md) owns cross-service contracts.

authBuddy issues homeBuddy account tokens. The UI proxies `/api/auth/` to authBuddy over the external `homebuddy` network; other `/api/` requests go to `calendar-api`. The API validates RS256 tokens against authBuddy's JWKS, fetched as `auth` over the internal `calendarbuddy-identity` network shared only with authBuddy (the API does not join `homebuddy`, so no other stack can reach it), and stores only an account projection keyed by the token subject. It does not store passwords or issue tokens. The API also joins the internal `calendarbuddy-metrics` network, shared only with the central Prometheus.

One account represents one family. Its members and appointments are private to that account, and every session of the account may edit them. PostgreSQL owns account projections, members, appointments, participants, recurrence rules, and exceptions. No calendar data is shared with finanzBuddy.

In local development, the UI uses port 3010, the API uses 8081, and PostgreSQL uses 5433. The production UI joins the external `homebuddy` network as `calendarbuddy-ui` and carries a `CALENDAR_DOMAIN` Traefik route. The root Traefik owns ports 80 and 443 on a shared host; the service-local Traefik profile is for standalone deployment.

## Data and API

Liquibase changesets create `accounts`, `family_members`, `appointments`, `appointment_participants`, and `appointment_exdates`. The API validates and applies all writes in transactions. Appointment participants use account-consistent foreign keys. A detached occurrence is an appointment row with `series_id` and `original_date`; a skipped occurrence is an exdate. The parent series version guards both kinds of change.

`/api/account` returns the account email and time zone. `/api/family-members` supports list, create, update, removal impact, and removal. `/api/appointments` supports CRUD and a range query with a 100-day cap and an optional member filter. Timed values are instants; all-day values are inclusive local dates. A range query uses a fixed number of queries: one-offs filtered by the range indexes, the account's series, detached occurrences and exdates near the range, and the participants of all candidates. Ranges are half-open, so an appointment ending at the range start is excluded. The recurrence engine expands daily, weekly, monthly, and yearly rules in the account time zone, period by period from the requested range, so open-ended series cost the same regardless of their age. It skips missing month days and preserves wall-clock time across daylight-saving transitions.

The React UI loads the account time zone from `/api/account` before rendering pages, stores the JWT in session storage, adds it to protected requests, and routes unauthorized users to sign-in with a return path. `/calendar` has month, week, and agenda modes with URL-backed date, view, and member state. `/family` manages member profiles. Both pages use the shared design anatomy documented in [the UI design system](../ui/DESIGN_SYSTEM.md).

## Local run

Start Rancher Desktop or another Docker engine. Create the external networks with `docker network create homebuddy` `docker network create --internal calendarbuddy-identity`, and `docker network create --internal calendarbuddy-metrics`, then start authBuddy. Set `POSTGRES_PASSWORD` and `CALENDAR_DOMAIN` in a local `.env` copied from `.env.example`, then run `docker compose up -d --build`. The UI is at `http://localhost:3010`; the API health endpoint is at `http://localhost:8081/actuator/health`.

## Delivery and releases

calendarBuddy follows the root capability `homebuddy-delivery` (see the [`delivery`](../openspec/specs/delivery/spec.md) capability): one `ci` check on pull requests to `main`, Conventional Commits pull-request titles, and release-please releases. Merging the release pull request tags `vX.Y.Z` and publishes `ghcr.io/rtcryo/calendarbuddy-calendar-api` and `ghcr.io/rtcryo/calendarbuddy-ui` with the tags `X.Y.Z` and `X.Y`, provenance attestations, and the digests in the release notes. Production runs those images: set `CALENDARBUDDY_VERSION` in `.env`, then run `docker compose -f docker-compose.yml pull` and `up -d`; the file does not build and fails naming the variable when it is missing. To roll back, set the previous version and run the same commands; if the newer release added a Liquibase changeset, roll that changeset back first, because an older image does not know the newer schema. `docker compose up --build` builds both components from the working tree and tags them `calendarbuddy-<component>:dev`.

## Metrics

`calendar-api` serves Prometheus metrics at `/actuator/prometheus` on port 8080 without a user token. The central Prometheus of the root stack scrapes `calendarbuddy-calendar-api:8080` over `calendarbuddy-metrics` (root capability `homebuddy-monitoring`); the path is not served through the UI proxy. Besides the standard HTTP and JVM metrics it exposes `calendarbuddy_appointment_operations_total` and `calendarbuddy_family_member_operations_total` (labels `operation`: `create`, `update`, `delete`; `outcome`: `success`, `conflict`, `invalid`), the gauges `calendarbuddy_appointments` and `calendarbuddy_family_members` (stored totals across all accounts, read at most every 15 seconds), and the timer `calendarbuddy_recurrence_expansion_seconds` (time spent expanding recurring appointments for one requested range). Operations are counted in the controllers, so requests rejected before reaching them, such as malformed bodies, are not counted. No metric carries an account id, member, title, or date. The dashboards live in the root `monitoring/` folder.
